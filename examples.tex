As a motivating example, we will show how our features for stepping
through programs can help clarify the execution of a map function.

A Hazel implementation of a map function over lists of integers is
given in \autoref{fig:hazel-map}. The full execution trace is shown in
\autoref{fig:full-trace}. It shows each of the small-step transitions
that are taken when evaluating this program.

Seeing the full length of the execution trace can be distracting. We may, for
example, only want to focus on the recursive calls. The Hazel stepper provides
some filter primitives that specify steps to hide. To more clearly show the
intuition behind the \code{map} function, we can hide all steps except those
that show the application of the \code{map} function, by inserting a
\code{debug hide} filter and a \code{debug stop} filter as shown in
\autoref{fig:hide-stop-map}.

  \centering
  \begin{subfigure}[T]{0.40\linewidth}

    \caption{The code from \autoref{fig:hazel-map} modified with extra \code{debug hide} and \code{debug stop} statements.}

  \end{subfigure}

Each filter has a pattern that triggers the filter. The \code{\$e}
pattern matches any expression, and the \code{\$v} pattern matches any
fully-evaluated expression. \code{map(\$v, \$v)} is a pattern that
matches any map expression applied to two fully-evaluated
expressions. More details on the patterns are given in the 
pattern matching judgment (\fbox{\(\Matches{p}{e}\)}).

The construct \code{debug hide} hides a step that matches the pattern, and thus
\code{debug hide(\$e)} hides all steps. The construct \code{debug stop} shows a
step that matches the pattern. Since it appears later in the program,
\code{debug stop(map(\$v, \$v))} overrides the preceding \code{debug hide} to show
any steps taken from an expression that contains a \code{map} applied
to two values.

The \code{debug hide} and \code{debug stop} constructs respectively hide or show only one
step. We also provide two more constructs, \code{debug eval} and
\code{debug step}, that hide or show all the evaluation steps for a
sub-expression that matches the given pattern.

For example, in \autoref{fig:debug-map} we have added a \code{debug step}
filter that shows the full trace of each application of \code{f}. We
can see in \autoref{fig:debug-trace} that this not only
shows steps that apply \code{f}, but also multiplications that
take place to evaluate \code{f(x)}.

\begin{figure}
  \centering
  \begin{subfigure}{0.40\linewidth}
    \frame{\includegraphics[scale=0.35]{images/eg31.png}}
    \Description{Map example with eval and step filters, including debug mode for square.}
    \caption{The code from \autoref{fig:hazel-map} modified with extra \code{debug hide}, \code{debug stop}, and \code{debug step} statements.}
    \label{fig:debug-map}
  \end{subfigure}
  \hfill
  \begin{subfigure}{0.57\linewidth}
    \frame{\includegraphics[scale=0.28]{images/eg32.png}}
    \Description{Filtered trace showing recursive map steps and explicit square evaluations on list elements.}

    \label{fig:debug-trace}
  \end{subfigure}
  \caption{A filtered stepper that demonstrates debug mode.}
\end{figure}

Note that this \code{debug step} statement overrides the \code{debug hide} and
\code{debug stop} statements because of the dynamic scoping of filters, which
is achieved by instrumenting the expression at every step and selecting the
closest filter to the part where the next step occurs (see
Step~\ref{num:simple_example_decompose} in
Section~\ref{sec:filter_example} for a more detailed description of
this).
